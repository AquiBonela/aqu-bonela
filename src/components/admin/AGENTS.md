- Procedure editing uses ordered JSON sections with nine typed elements and optional final notes; adapt legacy content and locale baselines in memory, preserving IDs and visibility, and save through the browser Supabase client under admin RLS. Spanish owns section structure and translations follow element IDs. The content summary remains the detail subtitle; independent cardDescription supplies card excerpts with legacy fallback. Why: flexible guides without schema changes, data loss or privileged credentials.
- Procedure image elements store immutable paths in private procedure-images storage; admin uploads reuse WebP conversion, visitors sign only exact paths referenced by visible published guides, and translations reuse the Spanish image. Display in a responsive 4:3 frame up to 672px with object-contain. Why: uniform illustrations without cropping or exposing drafts.
- Existing procedure guides remain available as unsaved editor templates until saved; only stored published guides appear publicly. Deletion of legacy guides writes an empty visibility.deleted marker excluded from editor/public lists and direct editor access. Why: prevent drafts or deleted guides from resurfacing without changing admin RLS or exposing draft content.
- ListingCategories owns the existing listing classification controls and is opened from the listing panel, not general settings. Why: keep classification next to the content it organizes without changing its persistence.
- Admin navigation is defined once in `admin-areas.ts`: eight areas (Inicio, Identidad municipal, Portada, Directorio, Servicios públicos, Actualidad, Descubre, Configuración) with inner sections matched by the longest path prefix; old URLs (`/admin/secciones`, `/admin/contenidos`, `/admin/contenidos/$pagina`) redirect. In public pages, the «Configuración» tab organises the page (sections and header) and other tabs edit content; areas whose content editors are not built yet say so without empty controls. `/admin` shows only indicators whose data loaded. Why: grow the panel by area with clear responsibilities and no invented figures.
- Municipal content screens use `useContentDraft(key, codec)` and `<DraftWorkflow>` (save, submit to the Town Hall, record conformity, return to draft, review and publish, discard); codecs in `src/lib/content-codecs.ts` write exactly the keys the database validates. Images chosen in a draft screen are uploaded only when the draft is saved (`prepare`), to new paths, and shown in the panel with signed URLs until published. Why: one circuit for every screen and no orphan uploads from merely choosing a file.
- The identity screen edits `site_identity` through the «identidad» draft, validating with the shared `identity-form` rules (the database re-checks them when submitting); logo and icons are part of the same draft and are generated in the browser. Postal code, colours and logo paths live in the same row; the palette is derived by `brand-palette.ts` with WCAG AA, and the screen previews the draft's header and colours. Why: identity changes need municipal conformity like any other public content.
- Page header images use the single `PageHeaderEditor` (draft «cabecera:<page>») inside each page's own screen (Portada › Presentación, Directorio › Presentación, Guía de trámites, and each page's Configuración); files live in private `site-assets` under a new path per upload and are served from `/marca/` with immutable caching once published. Why: one system for every page, safe replacement and cache-safe URLs.
- Configuración › Ajustes saves only Groundwork's internal settings, immediately, against the loaded `updated_at`, retrying once when only published columns changed meanwhile (`src/lib/internal-settings.ts`). Why: internal settings are not municipal content and must never overwrite a publication.
- Listing state shown in the panel combines `listings.status` with the owner review state deduced from `listing_events` (`listing_review_state`); the database rule `listings_publish_rule` (PT422) blocks publishing without owner approval except public services, so the UI only mirrors it (`canPublish`). Consents and requests are written only by SQL functions. Why: no accidental publication from any client, and an audit trail the browser cannot alter.
